# План: QR-маршруты (A) и хранение меток с удалением (B)

Дата: 2026-11-05. Статус: **A и B реализованы и выложены на `https://hotel`**.
Утверждённые варианты: таблица `QrCode` (одна активная метка), удаление QR только при удалении из справочника, вход до перехода по маршруту, статус «устарела» + ручная перегенерация.

---

## 1. Что проверено в коде

| Факт | Где | Следствие для решения |
|---|---|---|
| QR генерируется в памяти, не сохраняется | `server/trpc/routers/qr.ts:10-25`, `admin/qr/print/page.tsx:28-68` | для B нужна новая таблица/поля и файловое хранилище |
| Полей QR у `Room`/`Item` нет | `prisma/schema.prisma` | нужна миграция |
| Маршрутов `/r` и `/i` нет | `src/app` | A добавляется без конфликтов |
| Middleware закрывает только `/admin` и `/m` | `src/middleware.ts:8-10` | `/r` и `/i` могут быть публичными; проверку сессии делаем в route |
| **Форма входа игнорирует `callbackUrl` и всегда ведёт на `/`** | `components/login-form.tsx:31` | A требует доработки login: безопасный callback после входа |
| Удаление позиции — только `catalog.delete`, с защитой от истории | `routers/catalog.ts:95-122` | QR удаляем здесь; при списании позиция остаётся — QR удалять нельзя |
| Удаление номера — `rooms.deleteRoom`, с защитой от истории | `routers/rooms.ts:205-239` | QR номера удаляем здесь |
| Файлы фото лежат вне `public`, путь в БД, отдача через route | `lib/photos.ts`, `api/photos/[photoId]` | тот же паттерн применим к `storage/qr` |
| Печать генерирует все активные метки в память | `qr/print/page.tsx` | после B печать должна использовать сохранённые метки и создавать недостающие |

Важно: **«списание позиции» в текущей модели не удаляет позицию** — операция `WRITE_OFF` уменьшает остаток, запись `Item` остаётся. Удаление из справочника — отдельное действие `catalog.delete`, разрешённое только при нулевом остатке и отсутствии истории. Это развилка для утверждения (см. §6).

## 2. Вариант A — публичные маршруты

### 2.1 Маршруты

- `GET /r/[code]` — номер: поиск по `Room.number` или `Room.id`.
- `GET /i/[code]` — позиция: поиск по `Item.externalId`, `Item.id` или `Item.name`.
- Код нормализуется (`trim`, ограничение длины), декодируется из URL.
- Неизвестный код → `notFound()` (404).
- Деактивированный объект → страница «Объект деактивирован», без действий.

### 2.2 Авторизация и переходы

- Без сессии → `/login?callbackUrl=/r/<code>` (после правки login).
- После входа:
  - номер: ADMIN/MANAGER → `/admin/rooms`; MAID → `/m/rooms`;
  - позиция: ADMIN/MANAGER → `/admin/catalog`; MAID → `/m` (у горничной нет доступа к складу).
- `callbackUrl` принимается только как внутренний путь (`/...`, не `//...`), иначе `/`.
- Публичная страница не раскрывает остатки/цены — только переход.

### 2.3 Ограничения

- Rate limit на публичные маршруты (простой in-memory, как у логина) — опционально.
- Старые напечатанные метки после изменения номера/внешнего кода перестают разрешаться; для B можно хранить код в записи QR и поддерживать поиск по сохранённому коду.

## 3. Вариант B — хранение и привязка

### 3.1 Модель данных

Рекомендуемый вариант — отдельная таблица (не поля в `Room`/`Item`):

```
QrCode {
  id            String @id
  objectType    String   // ROOM | ITEM
  roomId        String?  // FK Room, onDelete Cascade
  itemId        String?  // FK Item, onDelete Cascade
  code          String   // код, зашитый в метку (номер / externalId / id)
  payload       String   // полная нагрузка
  payloadFormat String   // url | json | text
  imageFormat   String   // png | svg
  fileName      String?  // путь в storage/qr
  mimeType      String?
  sizeBytes     Int?
  baseUrl       String?  // NEXTAUTH_URL на момент генерации
  createdAt     DateTime
  updatedAt     DateTime
  @@unique([roomId])
  @@unique([itemId])
  @@index([objectType, code])
}
```

- Одна активная метка на объект; повторная генерация заменяет файл и запись.
- Отдельная таблица проще расширяется (версии, формат, аудит), не смешивается с доменом номера/позиции.
- Альтернатива B2 — поля `qrFileName/qrPayload/qrFormat/qrUpdatedAt` прямо в `Room`/`Item`: меньше JOIN, но хуже для истории и очистки.

### 3.2 Файлы

- `storage/qr/<room|item>/<objectId>/<timestamp>.<png|svg>` — вне `public`.
- В БД — относительный путь; отдача через авторизованный `/api/qr/[id]`.
- PNG/SVG генерируются через `qrcode` (как сейчас), файл пишется на диск, запись — в БД.
- При замене: новый файл → обновление записи → удаление старого файла (если есть).
- Осиротевшие файлы (сбой между шагами) — скрипт очистки/лог, не автоматическое удаление втихую.

### 3.3 Генерация и печать

- `/admin/qr` «Сгенерировать» → создаёт/обновляет `QrCode` + файл, показывает предпросмотр.
- Печать: для каждого активного объекта берёт сохранённую метку; если нет — создаёт; формат/размер из параметров; при несовпадении формата — перегенерация.
- В списках «Справочник» и «Номера» — бейдж «QR»/кнопка: есть метка или «создать».
- API скачивания: `/api/qr/[id]` с проверкой `rooms.read`; имя файла `qr-<type>-<code>.<ext>`.

### 3.4 Удаление

| Действие | Объект | Запись QrCode | Файл |
|---|---|---|---|
| `catalog.delete` (позиция без истории) | удаляется | удаляется (каскад/явно) | удаляется |
| `rooms.deleteRoom` (номер без истории) | удаляется | удаляется | удаляется |
| `WRITE_OFF` (списание остатка) | **остаётся** | **остаётся** | **остаётся** |
| деактивация (`isActive=false`) | остаётся | остаётся, помечается неактивной | остаётся |
| смена номера/externalId | остаётся | метка устаревает | требуется перегенерация |

Удаление файлов — после успешного удаления записи; ошибка `unlink` логируется, файл попадает в отчёт осиротевших. FS и SQLite не участвуют в одной транзакции — это осознанный компромисс.

### 3.5 Смена кода / домена

- При изменении `Room.number` или `Item.externalId` старая метка перестаёт разрешаться. Варианты: авто-перегенерация или статус «устарела» с предупреждением в списке (см. §6).
- Смена `NEXTAUTH_URL` меняет URL-нагрузку; PNG-метки с абсолютным URL устаревают. Нужно либо перегенерировать, либо использовать `json/text`-нагрузку (код без домена).

## 6. Вопросы на утверждение

| # | Вопрос | Варианты | Рекомендация |
|---|---|---|---|
| 1 | Модель хранения | отдельная `QrCode` / поля в `Room`/`Item` / `QrCode` с историей версий | **отдельная `QrCode`, одна активная на объект** |

| 3 | Доступ к `/r` и `/i` | сначала вход, затем переход / публичная карточка с кнопкой входа / публичная без входа | **сначала вход** (не раскрывает данные и сразу ведёт к действию) |

| 5 | Формат хранения файлов | PNG+SVG по требованию / только PNG / файл + payload в БД (без файла) | **PNG/SVG по выбору, один активный файл** |

## 7. Реализация и проверка

- **A:** `/r/[code]`, `/i/[code]`; `login` принимает только внутренний `callbackUrl`; после входа — роль-зависимый переход; 404 для неизвестного кода, отдельная страница для деактивированного объекта.
- **B:** миграция `20261105124546_qr_codes`; `QrCode` связан с `Room`/`Item` (`onDelete: Cascade`); файлы в `storage/qr/`; API `/api/qr/[id]`; графика сохраняется, повторная генерация обновляет ту же запись.
- **Удаление:** `catalog.delete` и `rooms.deleteRoom` удаляют запись и файл; `WRITE_OFF` и деактивация QR сохраняют.
- **Проверено:** 83 теста, build; Playwright `scripts/ui-qr.mjs`: login callback, роли, 404, сохранение/отдача PNG, повторная генерация, печать 10 меток, удаление тестовых позиции и номера; после теста 10 записей, 10 файлов, 0 осиротевших. Отдельно проверены статусы «устарела» → «актуальна».
