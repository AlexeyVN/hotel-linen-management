# План: раздел «Горничные» и удаление типа «Выездная»

Дата: 2026-11-05. Статус: **реализовано и выложено на `https://hotel`**.
Запрос: 1) раздел «Горничные» для менеджера — все горничные, статус работы, закреплённые номера, выполнение плана уборки, архив заданий по датам; 2) убрать тип уборки «Выездная»; 3) проверить зависимости и выдать на утверждение.

**Решения заказчика:** план — задачи, созданные в дату; вместо «Выездной» — тип **«По требованию» (ON_DEMAND)**, существующие CHECKOUT мигрируют в него; закрепление номеров — только просмотр; Excel архива — включить в этот этап.

### 1.2 Данные для «Горничных» — всё уже есть

| Источник | Поля | Использование |
|---|---|---|
| `User` + `Role` | роль MAID, `isActive`, ФИО, логин | список горничных |
| `UserRoom` | привязка горничная ↔ номер | закреплённые номера |
| `Shift` | `startedAt`, `endedAt` | статус смены |
| `CleaningTask` | тип, статус, assignee, room, план/факт времени, даты | план, текущая задача, архив |

Новых таблиц и полей **не требуется**. Индексы `CleaningTask(assigneeId,status)`, `(createdAt)` и `Shift(userId,endedAt)` уже есть — выборки по датам не требуют миграции схемы.

### 1.3 Права

`cleaning.manage` уже есть у ADMIN и MANAGER — новый раздел доступен менеджеру без изменения ролей. Горничная в админку не попадает (redirect на `/m`). Новые права не нужны.

## 2. Раздел «Горничные» (`/admin/maids`)

### 2.1 Что показываем

**Карточка/строка горничной:**

| Поле | Источник |
|---|---|
| ФИО, логин | User |
| Статус работы | вычисляется (см. 2.2) |
| Смена | открытая `Shift`: «с 09:15» / «не на смене» |
| Закреплённые номера | `UserRoom` → номера (номер, этаж, статус уборки) |
| План на дату | задачи, созданные в выбранную дату и назначенные горничной |
| Выполнение плана | `DONE / план × 100%`, «X из Y номеров», шкала прогресса |
| Выполнено сегодня | DONE за дату, уникальные номера |
| Среднее время | среднее (finishedAt − startedAt) по DONE за дату |
| Текущая задача | последняя IN_PROGRESS: номер, тип, с какого времени |

**Дата:** селектор даты (по умолчанию сегодня). План и статистика считаются за выбранную дату.

### 2.2 Статус работы (приоритет сверху вниз)

| Статус | Условие |
|---|---|
| `Неактивна` | `User.isActive = false` |
| `В работе` | есть задача IN_PROGRESS |
| `На смене` | открытая смена (`endedAt = null`) |
| `Не на смене` | открытой смены нет |

Если открытая смена висит больше 12 часов — показываем предупреждение «смена не закрыта» (не блокируем).

### 2.3 Формула плана

```
план      = задачи за дату (createdAt в дате), назначенные горничной,
            статусы NEW / IN_PROGRESS / DONE   (CANCELLED в план не входит)
выполнено = из плана со статусом DONE
процент   = план > 0 ? round(выполнено / план × 100) : null («—»)
номера    = уникальные roomId среди выполненных
```

Отменённые задачи показываем отдельным счётчиком, в знаменатель не включаем — иначе отказ горничной искусственно занижает план.

### 2.4 Архив заданий по датам

Отдельная карточка на той же странице:

- фильтры: горничная (все / конкретная), с даты, по дату, статус;
- таблица: дата создания, горничная, номер, тип, приоритет, статус, план/факт минут, начало, завершение;
- сортировка по дате создания (новые сверху), лимит 500 строк;
- суммарная строка по выбранным: всего / выполнено / отменено / среднее время.

Дата архива — **дата создания задачи** (как в существующем отчёте по уборке); факт завершения виден отдельной колонкой. Это согласуется с текущим отчётом `cleaning.report`.

### 2.5 API (расширение `cleaning`, без новой таблицы)

| Процедура | Вход | Выход |
|---|---|---|
| `cleaning.maidsOverview` | `{ date?: "YYYY-MM-DD" }` | список горничных: профиль, смена, комнаты, план/факт, текущая задача, статус |
| `cleaning.maidArchive` | `{ maidId?, from, to, status? }` | задачи за диапазон + сводка |

Право — `cleaning.manage`. Сервер считает статусы и проценты; UI только отображает (единый источник истины).

### 2.6 UI

- Новый пункт меню **«Горничные»** после «Уборки» (право `cleaning.manage`).
- Страница: шапка с датой, карточки горничных (grid), блок «Архив заданий» с фильтрами.
- Ссылки: из карточки — на `/admin/cleaning` (текущая задача), из архива — на задачу в списке уборки.
- Мобильный кабинет не меняется.

### 2.7 Чего НЕ делаем в этом этапе (если не утвердите иное)

- Редактирование закрепления номеров на странице «Горничные» — остаётся в «Пользователях» (там право `users.manage`, у менеджера его нет). На странице — только просмотр.
- Excel-выгрузка архива горничных — можно добавить отдельным пунктом (сейчас Excel есть для уборки).
- Нормативы времени и KPI-рейтинги — вне объёма.

## 3. Тип «Выездная» → «По требованию»

По решению заказчика тип не удаляется, а переименовывается: `CHECKOUT` → `ON_DEMAND`, подпись «По требованию». Итоговый справочник: `DAILY`, `ON_DEMAND`, `GENERAL`.

1. `CLEANING_TYPES` → `DAILY`, `ON_DEMAND`, `GENERAL`; `CLEANING_TYPE_LABELS` без CHECKOUT, с «По требованию».
2. `typeSchema` → `z.enum(["DAILY","ON_DEMAND","GENERAL"])`; API отклоняет CHECKOUT.
3. Форма создания задачи: три типа, без «Выездная».
4. Seed: демо-задача 202 → `ON_DEMAND`.
5. Миграция данных: `UPDATE CleaningTask SET type='ON_DEMAND' WHERE type='CHECKOUT'`.
6. Обновить комментарий схемы и тест `reports-excel`.
7. Проверить мобильные списки/детали и Excel — подписи через общий словарь.

## 6. Риски

1. **План зависит от даты создания задачи.** Если задачу создали вчера, а убрали сегодня — в сегодняшний план она не попадёт. Альтернатива — считать по `finishedAt`; рекомендуется текущий вариант (план = назначенные на дату задачи), в архиве видно обе даты.
2. **Незакрытые смены** могут висеть сутками. Показываем предупреждение; авто-закрытие не делаем.
3. **Историческая семантика CHECKOUT:** после миграции старые выездные станут генеральными. Это осознанно; альтернатива — оставить исторический тип только для чтения.
4. **Объём архива:** лимит 500 строк; при необходимости — пагинация/Excel отдельным шагом.
