# План: обмен статусами номеров с «1С:Отель»

Дата: 2026-11-05. Статус: **реализовано в конфигурируемом виде и проверено на mock**; боевой контракт 1С ожидает подтверждения.
Утверждено: конфигурируемый путь/метод + mock, `X-Webhook-Token`, без автосоздания задач, все локальные изменения статуса в очередь, кнопка переименована.
Запрос: выяснить функцию кнопки «Синхронизировать номенклатуру»; проверить возможность получать из 1С номер/статус (чистый/грязный) и отправлять статус из приложения горничной.

---

## 1. Что сейчас делает кнопка «Синхронизировать номенклатуру»

Цепочка: `integration-admin.tsx` → `integration.syncItemsNow` → `syncItems()`.

`syncItems()`:

1. Берёт `lastSyncAt` из настроек.
2. Вызывает `GET {base}/hs/hotel/items?since=...` с Basic Auth.
3. Создаёт/обновляет `Item` по `externalId`, категории и `WarehouseInventory`.
4. Записывает `integration.lastSyncAt`, очищает `lastError`.

Чего кнопка **не делает**:

- не отправляет операции (для этого отдельная кнопка «Отправить очередь»);
- не читает и не меняет `Room.cleaningStatus`;
- не создаёт задачи уборки;
- не является «полной синхронизацией» — это только импорт номенклатуры.

Воркер раз в минуту досылает outbox операций; номенклатуру обновляет по `syncIntervalMinutes`, если прошёл интервал. Outbox сейчас привязан к `Operation` (`operationId @unique`) и для статусов номеров не подходит.

Вывод: текущая кнопка к задаче статусов номеров отношения не имеет. Её стоит переименовать в **«Загрузить номенклатуру»**, а обмен статусами вынести в отдельный блок.

## 2. Что удалось подтвердить по «1С:Отель»

Публичной спецификации именно `Housekeeping/v1/SetRoomStatus` и вебхуков статусов номеров в открытых источниках найти не удалось. Вендор документирует интеграции через **публикуемые HTTP-сервисы** и настройку внешней системы в подсистеме «Интеграции»:

- пример интеграции Hotellab: нужно опубликовать HTTP-сервис, указать адрес публикации `http://server:port/publication` и настроить интеграцию в 1С — [support.1chotel.ru](https://support.1chotel.ru/knowledge_base/item/267651?b_from_widget=1?sid=72098);
- общая информация о решениях/интерфейсах — [1c-hotel.ru](https://1c-hotel.ru/), [solutions.1c.ru](https://solutions.1c.ru/catalog/hotel).

Это подтверждает архитектуру «опубликованный HTTP-сервис + Basic Auth», но **не подтверждает** точный путь `/hs/Housekeeping/v1/SetRoomStatus`, имена полей JSON и наличие готовых вебхуков. Их нужно согласовать с внедренцем 1С/вендором для конкретного релиза.

Поэтому реализация должна быть **конфигурируемой** и проверяться на мок-сервисе; боевой контракт фиксируется после ответа 1С. Если вебхуки в релизе отсутствуют — предусмотреть резервный polling/агент на стороне 1С.

## 3. Предлагаемая архитектура

### 3.1 Приём: 1С ➔ система

`POST /api/integrations/1c/room-status` (JSON).

Пример канонического payload:

```json
{
  "eventId": "1c-2026-11-05-000123",
  "eventType": "room.status.changed",
  "roomNumber": "101",
  "status": "DIRTY",
  "occurredAt": "2026-11-05T16:20:00+03:00"
}
```

Поддержать алиасы полей (`roomNumber`/`number`, `status`/`cleaningStatus`), но после согласования зафиксировать один контракт.

- Авторизация: `X-Webhook-Token` (рекомендуется) или Basic; токен хранится зашифрованным, генерируется в админке.
- Валидация: номер существует и активен; статус из маппинга; `occurredAt` валиден.
- Идемпотентность: уникальный `eventId`; повтор → 200 без изменения.
- Устаревшее событие (старше локального `cleaningStatusUpdatedAt`) игнорируется с записью в журнал.
- Inbound-событие **не ставит** outbound в очередь — защита от петли.
- Ответы: 200 `{ok:true, applied:true|false}`; 400/401/404 с понятной ошибкой.

### 3.2 Передача: система ➔ 1С

При изменении статуса из UI (завершение задачи, `setRoomStatus`, создание задачи → DIRTY) создаётся запись в outbound-очереди.

Адаптер:

```
POST/PUT {base}{roomStatusPath}
Basic Auth (логин/пароль интеграции)
Body: { roomNumber, status, statusCode?, eventId, occurredAt, source: "hotel-linen" }
```

- `roomStatusPath` по умолчанию `/hs/Housekeeping/v1/SetRoomStatus`, настраивается.
- Метод `POST`/`PUT` — настройка (релизы 1С различаются).
- 2xx — `SENT`; 4xx — `FAILED` (без бесконечных ретраев); 5xx/таймаут — `PENDING` с backoff (как у операций).
- Воркер отправляет очередь; кнопка «Отправить статусы» — ручной досыл.
- Если интеграция выключена — очередь не создаётся/не отправляется, локальная работа продолжается.

### 3.3 Модель данных

Добавить:

- `Room.cleaningStatusUpdatedAt DateTime` (или отдельное поле) и, при необходимости, `cleaningStatusSource` — для защиты от устаревших webhook-событий.
- `RoomStatusEvent`:
  - `id`, `roomId`, `direction` (`INBOUND`/`OUTBOUND`), `eventId` (unique), `status`, `occurredAt`, `source`, `state` (`APPLIED`/`PENDING`/`SENT`/`FAILED`), `attempts`, `lastError`, `externalRef`, `createdAt`, `updatedAt`.
  - журнал аудита и дедупликация.
- Outbound-очередь можно хранить в этой же таблице (`direction=OUTBOUND`, `state=PENDING`), без изменения `OutboxEntry` (он привязан к операциям).

### 3.4 Маппинг статусов

| 1С (алиасы) | Система |
|---|---|
| `CLEAN`, `clean`, `Чистый`, `Убран` | `CLEAN` |
| `DIRTY`, `dirty`, `Грязный`, `Требует уборки` | `DIRTY` |
| `INSPECTED`, `inspected`, `Проверен` | `INSPECTED` |
| `OUT_OF_ORDER`, `repair`, `Ремонт`, `В ремонте` | `OUT_OF_ORDER` |

Неизвестное значение — 400 и запись в лог, без «молчаливого» дефолта. Точные коды 1С согласовать; при необходимости — таблица соответствий в настройках.

### 3.5 Где менять UI

На `/admin/settings/1c`:

- кнопка «Загрузить номенклатуру» (бывшая «Синхронизировать…»);
- блок **«Статусы номеров»**: включить обмен, URL вебхука (скопировать), токен (сгенерировать/замаскировать), путь и метод SetRoomStatus, интервал/статус очереди;
- тестовая отправка известного статуса на мок/1С;
- счётчики: получено, отправлено, ошибки, последняя ошибка;
- предупреждение, если 1С не подтвердила контракт.

На `/admin/cleaning` и в мобильном кабинете — небольшой индикатор синхронизации комнаты (опционально, без блокировки действий).

## 5. Критерии приёмки

1. 1С отправляет webhook → номер в системе меняет статус; повтор с тем же `eventId` не меняет ничего.
2. Неизвестный номер/статус → 4xx, запись в журнал, данные не испорчены.
3. Устаревшее событие не перетирает более новый статус.
4. Горничная завершает уборку → статус `CLEAN` уходит в 1С; при 5xx остаётся в очереди, при 4xx — `FAILED`.
5. Кнопка «Отправить статусы» досылает очередь; выключенная интеграция не мешает учёту.
6. Нет петли: inbound не порождает outbound; повторный webhook не создаёт дубль.
7. «Загрузить номенклатуру» по-прежнему обновляет только номенклатуру.
8. Тесты/build зелёные; секреты не логируются.

## 6. Риски

1. **Точный контракт 1С не подтверждён** — путь/поля могут отличаться; обязательна настройка и mock.
2. **Webhooks могут отсутствовать** в релизе — нужен polling/агент или ручной триггер.
3. **Basic Auth** для вебхука не всегда удобен 1С; нужен shared token/заголовок.
4. **Петля статусов** — решается направлением события и дедупом.
5. **Гонки**: webhook и локальное изменение одновременно — сравнение `occurredAt` и транзакция.
6. **Права 1С**: пользователь должен иметь доступ к Housekeeping/Rooms; иначе 403.
