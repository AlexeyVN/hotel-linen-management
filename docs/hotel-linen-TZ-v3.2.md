| # | Раздел v2.1 | Проблема | Решение в v2.2 |

## 2. Термины

| Термин | Значение |
|---|---|
| Позиция (Item) | Учитываемая единица: комплект белья, бутыль химии, инвентарь |
| Остаток | Сумма операций по позиции в данном месте (склад или номер) |
| Приёмка (RECEIVE) | Поступление от поставщика на склад |
| Раздача (DISTRIBUTE) | Перемещение со склада в номер |
| Возврат (RETURN) | Перемещение из номера на склад |
| Списание (WRITE_OFF) | Уменьшение остатка без получателя (порча, износ) |
| Инвентаризация (AUDIT) | Сверка факта с учётом; расхождение порождает корректировку |
| Операция | Атомарный документ: тип, строки позиций, автор, время |
| Расхождение | `факт − учёт` по позиции в инвентаризации |

## 4. Архитектура и размещение

```
Телефон (PWA) ─┐
               ├─ https://hotel ─→ Apache (OSPanel, mod_proxy)
ПК админа ─────┘                                              │
                                                              ▼
                                              Node: next start 127.0.0.1:3000
                                                              │
                                        ┌─────────────────────┼───────────────────┐
                                        ▼                     ▼                   ▼
                                  data/app.db          storage/photos/      1С HTTP-сервис
                                  (SQLite, WAL)        (вне public)         (outbox, опц.)
```

| Путь | Назначение |
|---|---|
| `C:\OSPanel\home\hotel\app\` | проект Next.js |
| `...\app\data\app.db` | база (вне `public`, бэкап — `VACUUM INTO`) |
| `...\app\storage\photos\YYYY\MM\` | фотофиксация, отдача только через авторизованный route handler |

| `...\app\backups\` | дампы БД |
| `...\deploy\` | конфиги прокси, `start.cmd`, инструкции |

**Поток запроса:** браузер → прокси → Node → tRPC/Server Action → Zod → Prisma/БД. Прав проверяются на сервере в каждом обработчике; клиентский RBAC — только UX.

**Сетевые правила:** Node слушает `0.0.0.0:3000` (иначе телефоны в Wi-Fi не достучатся); в брандмауэре — правило на порт 3000 для локальной подсети; наружу порт не публикуется.

## 5. Модель данных

### 5.1 Сущности

| Модель | Поля (ключевые) | Правила |
|---|---|---|
| `User` | id, login (unique), passwordHash, fullName, roleId, isActive, lastLoginAt, failedLogins, lockedUntil | login ≥ 4 симв.; удаление — soft (`isActive=false`), чтобы не рвать историю операций |
| `Role` | id, code (unique), name, isSystem | 3 системных пресета + возможность создавать свои |
| `Permission` | id, code (unique), description | коды — §6.1 |
| `RolePermission` | roleId, permissionId | `@@unique([roleId, permissionId])`, каскад от `Role` |
| `UserRoom` | userId, roomId | привязка горничной к номерам; `@@unique([userId, roomId])` |
| `RoomType` | id, code (unique), name, isActive | для `MinStock`; **редактируется администратором** (добавление/переименование/деактивация), а не зашитый enum |
| `Room` | id, number (unique), floor (Int?), floorName (String?), roomTypeId, isActive | ровно одно из floor/floorName; `@@index([floor])`, `@@index([roomTypeId])`, каскад от `RoomType` — запрещён (`Restrict`) |
| `Category` | id, code, name | `code ∈ {LINEN, CHEMICAL, ITEM}` — валидируется Zod |
| `Item` | id, name, categoryId, unit, externalId (unique, nullable), isActive | `externalId` — код номенклатуры 1С; `@@index([categoryId])` |
| `WarehouseInventory` | itemId (unique), qty, version, updatedAt | qty ≥ 0; оптимистическая блокировка по `version` |
| `RoomInventory` | roomId, itemId, qty, version, updatedAt | `@@unique([roomId, itemId])`, `@@index([roomId])`; qty ≥ 0 |
| `Operation` | id, type, roomId (nullable), userId, clientOpId (unique, nullable), comment, reason (обязателен для WRITE_OFF), createdAt | типы: RECEIVE / DISTRIBUTE / RETURN / WRITE_OFF / AUDIT; `@@index([createdAt])`, `@@index([type])`, `@@index([roomId])`; операция неизменяема, ошибка исправляется обратной операцией |
| `WriteOffReason` | id, code (unique), name, isActive | справочник причин списания; в форме можно выбрать причину или ввести свой текст |
| `OperationItem` | operationId, itemId, qty, expectedQty, factQty, delta | `@@index([itemId])`; для AUDIT заполняются expected/fact, для остальных — только `qty` |
| `AuditSession` | id, roomId, userId, status (DRAFT/APPLIED), startedAt, appliedAt | черновик можно править; после APPLIED — только через обратную операцию |
| `Photo` | id, auditSessionId, fileName, mimeType, sizeBytes, createdAt | файл вне `public`; mime ∈ {jpeg,png,webp}, ≤ 5 МБ |
| `MinStock` | itemId, roomTypeId, minQty | `@@unique([itemId, roomTypeId])`; низкий остаток = `RoomInventory.qty < minQty` |
| `OutboxEntry` | id, operationId, status (PENDING/SENT/FAILED), attempts, lastError, nextAttemptAt, createdAt | `@@index([status, nextAttemptAt])`; экспорт в 1С |
| `Setting` | key (unique), value, updatedAt | интеграция 1С, пороги, прочее — без пересборки |

### 5.2 Правила уровня БД

1. `updatedAt` — автообновление на уровне Prisma (`@updatedAt`).
2. Каскады: `Role`→`RolePermission` cascade; `Category`→`Item` — `Restrict` (нельзя удалить категорию с позициями); `Item`→`WarehouseInventory`/`RoomInventory` cascade при удалении позиции (но позиции деактивируются, а не удаляются); `Operation`→`OperationItem` cascade; `Operation` никогда не удаляется.
3. Индексы: `Operation(createdAt)`, `Operation(type)`, `Operation(roomId)`, `RoomInventory(roomId)`, `OperationItem(itemId)`, `OutboxEntry(status,nextAttemptAt)`, `Item(externalId)`.
4. Количества — `Int`, `qty ≥ 0` проверяется в сервисном слое и Zod; отрицательный остаток запрещён.
5. Enum-значения (`Operation.type`, `Category.code`) объявлены в Prisma, но БД их не проверяет → Zod-валидация обязательна на всех входных точках; миграция с `CHECK`-констрейнтами допускается как усиление.
6. Идемпотентность: `Operation.clientOpId` — unique; повтор запроса с тем же ключом возвращает исходный результат, а не создаёт дубль (PWA-очередь, двойной клик, ретраи).
7. Оптимистическая блокировка: изменение остатка идёт в транзакции с проверкой `version`; при конфликте — 409 и повтор с перечитыванием.
8. Seed идемпотентен (upsert по естественным ключам): **3 этажа, 10 номеров, 3 типа комнат, 3 категории, ~10 позиций, 3 пользователя** (`admin`/`manager`/`maid`), минимальные остатки. Расчётный масштаб — до 30 номеров и 3 этажей; seed намеренно меньше, чтобы демо-данные не мешали реальной работе.

## 7. Модули и критерии приёмки

Формат: **Модуль → критерии**. Критерий считается выполненным только при фактическом прогоне.

### 7.1 Вход и права

- Вход `admin/manager/maid` → своя стартовая страница; неверный пароль → сообщение без раскрытия существования логина.
- 10 неверных попыток за 10 минут → блокировка на 15 минут (по IP+логину).
- Прямой запрос страницы без сессии → редирект на `/login`; tRPC-вызов без права → 403, а не 500.
- Деактивированный пользователь теряет доступ при следующем запросе.

### 7.2 Номера

- Список с фильтрами по этажу и типу, поиск по номеру; добавление, редактирование, деактивация.
- Попытка создать дубликат номера → понятная ошибка, не 500.
- Деактивированный номер исчезает из выбора при раздаче, но остаётся в истории.

### 7.3 Склад: приёмка

- Приёмка из 3 позиций атомарно увеличивает остатки склада; при ошибке в одной строке не применяется ни одна.
- История приёмок с автором и временем; операция не удаляется.
- Повторная отправка той же приёмки с тем же `clientOpId` не удваивает остаток.

### 7.4 Раздача и возврат

- Раздача уменьшает склад и увеличивает остаток номера в одной транзакции.
- Раздача больше остатка отклоняется с указанием доступного количества.
- Возврат уменьшает остаток номера и увеличивает склад; возврат больше остатка номера отклоняется.
- В отчёте движений видны обе стороны.

### 7.5 Списание

- Списание уменьшает остаток склада или номера; причины — из справочника (порча, износ, загрязнение, утеря, бой) либо свободным текстом. **Причина обязательна**, автор фиксируется.
- Списывать вправе администратор и менеджер (`writeoff.create`); горничная — нет.
- Списанное не восстанавливается редактированием — только новой операцией.

### 7.6 Инвентаризация

- Выбор номера → таблица текущих остатков по позициям → ввод фактических количеств → фотофиксация (1..N снимков) → применение.
- Расхождение формирует корректировку остатка номера и попадает в отчёт; в истории видно `учёт / факт / расхождение`.
- Черновик можно сохранить и вернуться; после применения — запрет правки.
- Обязательность фото — флаг `audit.photoRequired`, **по умолчанию выключен** (решение заказчика: фото не обязательно).

### 7.7 Отчёты

- Остатки склада с фильтром по категории; движения за период с фильтром по типу и номеру; низкий остаток по правилу `MinStock` для типа комнаты.
- Выгрузка на экран/печать; Excel — вне v2.2.
- Пустой период — «нет данных», не ошибка.

### 7.8 Настройки 1С

- Форма URL/логин/пароль; проверка соединения кнопкой; синхронизация номенклатуры («Синхронизировать сейчас» + по расписанию); статус очереди и последних ошибок.
- Отключение интеграции → фоновые задачи прекращаются, операции продолжают учитываться локально, при повторном включении очередь догоняет.

### 7.9 PWA горничной

- Главная: две крупные кнопки («Инвентаризация», «Раздача»), TabBar, шапка с именем и выходом.
- Инвентаризация: список своих номеров → остатки → ввод факта → фото → отправка.
- Раздача: выбор номера + количества из доступного на складе.
- На экране 360×640 (типичный телефон) нет горизонтальной прокрутки; кнопки ≥ 44 px по высоте.
- Установка PWA: при HTTPS — «Добавить на главный экран», запуск в standalone.
- Офлайн: без сети открывается оболочка, доступны последние данные, отправка ставится в очередь; после появления сети операция применяется ровно один раз (проверка: остаток изменился на одну порцию, не на две).

## 8. Интеграция с 1С Отель

### 8.1 Реалии канала (почему не WebSocket)

1С Отель не публикует WebSocket-канал по умолчанию. Требование «реальное время» в v2.1 не опиралось на подтверждённый интерфейс. В v2.2:

| Направление | Механизм |
|---|---|
| Номенклатура 1С → система | Pull по расписанию (по умолчанию 5 мин) + кнопка «Синхронизировать сейчас»; сопоставление по `externalId`, создание/обновление `Item` |
| Операции → 1С | `OutboxEntry`: операция сначала фиксируется локально, затем отправляется; ретраи с экспоненциальной задержкой (1, 2, 4, ... до 30 мин, максимум 8 попыток) |
| Статус в UI | SSE-поток от нашего сервера: `pending / sent / failed` — это и есть «реальное время» для пользователя |

### 8.2 Настройка

Форма в админке: `baseUrl`, логин, пароль (хранится в `Setting`, в БД/логах не печатается), интервал синхронизации, переключатель «Интеграция включена». Пароль в UI показывается как «задан/не задан», не открытым текстом.

### 8.3 Инварианты

1. Учёт не зависит от 1С: при недоступности 1С операции работают, очередь растёт.
2. Повтор отправки не создаёт дубль: уникальный `clientOpId`/`operationId` передаётся в 1С как ключ идемпотентности.
3. Отключение интеграции не удаляет очередь и не меняет остатки.
4. Все обмены логируются: время, направление, код ответа, объём, текст ошибки (без паролей).

### 8.4 Статус эндпоинта

Формат эндпоинта 1С (OData-стандарт / собственный HTTP-сервис / обмен через файл) заказчик пока не предоставил. Адаптер реализован против контракта §8.5 и проверен на моке HTTP-сервиса (`scripts/mock-1c.mjs`) с протоколом:

- `GET {base}/hs/hotel/ping` — проверка соединения;
- `GET {base}/hs/hotel/items?since=<ISO>` — `[{ code, name, unit?, category? }]`;
- `POST {base}/hs/hotel/operations` — DTO операции, ответ `{ ok, ref }`;
- авторизация Basic (логин/пароль из настроек).

При другом протоколе меняется только реализация `OneCAdapter` (`src/server/erp/adapters/onec.ts`), остальная система не затрагивается.

### 8.5 Контракт адаптера (фиксируется в коде)

```
interface ErpAdapter {
  ping(): Promise<{ ok: boolean; details?: string }>;
  pullItems(since?: string): Promise<Array<{ externalId: string; name: string; unit: string; categoryCode: string }>>;
  pushOperation(op: { id: string; type: string; roomNumber?: string; items: Array<{ externalId: string; qty: number }>; createdAt: string }): Promise<{ ok: boolean; externalId?: string; error?: string }>;
}
```

Реализации: `OneCAdapter` (по факту эндпоинта) и `StubAdapter` (тесты и демо).

### 8.6 Реализовано в M5

| Требование | Реализация |
|---|---|
| Настройка подключения | Раздел «Интеграция 1С» в админке: режим (заглушка/1С), URL, логин, пароль, интервал, включение |
| Пароль не раскрывается | AES-256-GCM, ключ из `NEXTAUTH_SECRET`; в API/UI — только «задан/не задан» |
| Синхронизация номенклатуры | Ручная кнопка + воркер по интервалу; позиции сопоставляются по `externalId` |
| Экспорт операций | `OutboxEntry` (`PENDING`/`SENT`/`FAILED`), отправка по порядку, идемпотентность по `clientOpId` |
| Ретраи | Экспоненциальная задержка 1 с → 30 мин, максимум 8 попыток, затем `FAILED` с текстом ошибки |
| 1С недоступна | Учёт продолжает работать, очередь растёт; ошибка видна в настройках |
| Отключение | Флаг `integration.enabled=false`: воркер и ручные отправки прекращаются, данные сохраняются |
| Диагностика | Статус (включена/режим/очередь/последняя синхронизация/последняя ошибка), `POST /api/integration/worker` для внешнего планировщика |

## 9. PWA и офлайн-режим

### 9.1 Что кэшируется

| Объект | Стратегия |
|---|---|
| Оболочка (HTML/JS/CSS/иконки) | precache при установке SW, версия в имени кэша |
| `/api/manifest` | network-only, `no-store` (название отеля меняется без пересборки) |
| Справочники (свои номера, позиции, последние остатки) | cache-first + обновление при онлайне |
| Записи (инвентаризация, раздача) | **не кэш**, а очередь в IndexedDB |

### 9.2 Очередь мутаций

- Каждая запись: `{ id (uuid), type, payload, clientOpId, createdAt, attempts }`.
- При появлении сети — отправка по порядку; `clientOpId` гарантирует идемпотентность (п. 5.2.6).
- Успех → запись удаляется из очереди, данные перезапрашиваются.
- Ошибка 4xx (валидация, нет остатка) → запись помечается `conflict`, показывается оператору, повтор не автоматический.
- Ошибка 5xx/сеть → повтор с задержкой, максимум 8 попыток, затем `failed` с ручным повтором.
- **Конфликты не сливаются автоматически**: две горничные в одном номере → вторая запись уходит на ручной разбор (принцип: лучше отказ, чем тихая потеря).

### 9.3 Обновление SW

Новая версия регистрируется, активируется по кнопке «Обновить приложение»; старый кэш удаляется. Принудительная активация без согласия не делается (чтобы не порвать введённые данные).

### 9.4 HTTPS — блокирующее требование для установки PWA

Service Worker и «Добавить на главный экран» работают только в secure context. Варианты на LAN:

| Вариант | Что делаем | Цена |
|---|---|---|
| **A. Самоподписанный сертификат на домен** (рекомендуется) | OSPanel раздаёт HTTPS по локальному сертификату; на телефонах один раз устанавливается корневой сертификат | ручные действия на каждом телефоне |
| B. HTTPS через доверенный локальный CA | Полноценный локальный CA, сертификат на `*.hotel.local` | настройка CA, установка корня на телефонах |
| C. Только учёт без установки PWA | Приложение работает по `http://<LAN-IP>:3000`, SW не регистрируется | нет офлайна и иконки на экране |
| D. Временный тестовый обход | Флаг Chrome «небезопасный origin как защищённый» | только разработка, не для горничных |

**Выбрано заказчиком (2026-11-04): вариант A.** OSPanel раздаёт домен по HTTPS с самоподписанным сертификатом; на каждом телефоне один раз устанавливается корневой сертификат (инструкция и генерация сертификата — в этап M5, `deploy/`). Код при этом не зависит от выбора: при `http://` приложение работает как обычный сайт, но без SW и установки на главный экран.

## 10. Нефункциональные требования

### 10.1 Объёмы (расчётная нагрузка)

До 300 номеров, до 500 позиций, до 10 одновременных пользователей, до 50 000 операций в год (~3 ГБ данных за 5 лет с фото). SQLite с WAL это выдерживает; узкое место — параллельная запись (одна за раз), поэтому транзакции короткие, а тяжёлые отчёты не блокируют запись.

### 10.2 Производительность

- Серверный ответ tRPC на локальной сети: p95 ≤ 500 мс для операций, ≤ 1 с для отчётов за месяц.
- Первая загрузка PWA на телефоне в Wi-Fi: ≤ 3 с до интерактивной главной.
- Список номеров/позиций — серверная пагинация при > 200 строк.

### 10.3 Безопасность

| Угроза | Мера |
|---|---|
| Подбор пароля | bcrypt (cost 12), блокировка после 10 попыток/10 мин, лимит на IP+логин |
| SQL-инъекция | Только Prisma (параметризация); сырой SQL — запрещён без обоснования |
| XSS | React-экранирование; `dangerouslySetInnerHTML` — запрещён; CSP-заголовок |
| CSRF | Встроенная защита next-auth + `sameSite=lax`, httpOnly-cookie |
| Доступ к файлам | Фото вне `public/`, отдача через route handler с проверкой права и владельца |
| Загрузка файлов | MIME ∈ {jpeg,png,webp}, ≤ 5 МБ, имя генерируется, EXIF срезается, содержимое проверяется по сигнатуре |
| Утечка секретов | `.env` вне репозитория, пароль 1С не логируется, в UI — «задан/не задан» |
| Перебор API | Rate limit: 60 мутаций/мин на пользователя, 10 попыток входа/10 мин на IP+логин (in-process, single-node) |

### 10.4 Логирование

- pino в `logs/app-YYYY-MM-DD.log`, 14 дней; уровень `info` в проде, `debug` — флагом.
- Логируются: вход/выход, отказ в правах, ошибки сервера с `correlationId`, операции 1С, конфликты офлайн-очереди.
- Не логируются: пароли, хэши, токены, содержимое cookie.

### 10.5 Бэкап и восстановление

- `deploy/backup.cmd` → `sqlite3 data/app.db "VACUUM INTO 'backups/app-YYYYMMDD-HHMMSS.db'"`; запуск по расписанию (Task Scheduler/cron).
- Копирование `.db` при включённом WAL даёт неконсистентный файл — **запрещено**; допускается `VACUUM INTO` или `.backup`.
- `deploy/restore.cmd`: остановить сервис, сохранить текущую БД, развернуть дамп, проверить `PRAGMA integrity_check`, запустить сервис.
- Проверка восстановления — обязательный шаг приёмки (не реже раза на этап).

### 10.6 Надёжность

- Автозапуск Windows: Startup `hotel-linen-autostart.cmd`; на Linux — systemd с `Restart=always` (см. `docs/DEPLOYMENT.md`).
- Ошибка в обработчике → 500 с `correlationId`, пользователю — понятное сообщение, в лог — стек.
- Миграции применяются до старта (`prisma migrate deploy`), откат — из бэкапа.

## 13. Инструкция по запуску (исправленная)

> Раздел 8 v2.1 («Document Root = ...\public», «заходим на http://hotel-linen-management» без Node-процесса) нерабочий: статикой Next.js не поедет. Ниже — рабочая последовательность.

1. **Node.js 24.x** установлен (проверка: `node -v`). npm вызывается как `npm.cmd` — `npm.ps1` блокируется Execution Policy.
2. Проект размещён в `C:\OSPanel\home\hotel\app`.
3. `cd C:\OSPanel\home\hotel\app` → `npm.cmd ci`.
4. Создать `.env` (не коммитить): `DATABASE_URL="file:../data/app.db"`, `NEXTAUTH_URL="https://hotel"`, `NEXTAUTH_SECRET="<сгенерировать>"`, `TZ="Europe/Moscow"`.
5. Применить схему: `npx.cmd prisma migrate deploy`, затем `npm.cmd run db:seed`.
6. Сборка: `npm.cmd run build`.
7. Запуск: `npm.cmd run start` (слушает `0.0.0.0:3000`). Автозапуск — Startup `hotel-linen-autostart.cmd` (OSPanel + Node).
8. **Домен OSPanel:** `https://hotel` → Apache reverse proxy на `http://127.0.0.1:3000`; `Document Root` не задаётся. Статика Next отдаётся через junction `_next`/`icons` и копию `sw.js`; manifest — динамический `/api/manifest` через прокси (см. `docs/DEPLOYMENT.md`).
9. Открыть `https://hotel` (или `http://127.0.0.1:3000`). Вход: `admin` / пароль из seed (сменить при первом входе).
10. **С телефона:** HTTPS по домену; корневой сертификат установить один раз; затем `https://hotel` → PWA. Обходной путь — `http://<LAN-IP>:3000` без SW/PWA.
11. Бэкап: `deploy\backup.cmd` по расписанию; восстановление — `deploy\restore.cmd` (сервер остановить).

## 15. Хаускипинг (v2.4, после анализа рынка)

Основание: [анализ практик Bnovo/TeamJet и ME Hotel](../docs/analysis-housekeeping-market-2026-11-05.md) и решение заказчика от 2026-11-05 — **вариант 1, без чек-листов**: достаточно статусов номеров и задач на уборку.

### 15.1 Модель

| Сущность | Поля | Правила |
|---|---|---|
| `Room.cleaningStatus` | CLEAN / DIRTY / INSPECTED / OUT_OF_ORDER | Статус номера для доски и администратора |
| `CleaningTask` | номер, тип (DAILY / CHECKOUT / GENERAL), приоритет (URGENT / MEDIUM / LOW), статус, исполнитель, автор, план/факт минут, комментарий | Задача — отдельная сущность, не операция склада |
| `Shift` | горничная, начало/конец смены | «Начать смену» на мобильном экране |

### 15.2 Правила

1. Создание задачи помечает номер `DIRTY` (кроме `OUT_OF_ORDER`).
2. «В работе» — номер `DIRTY`; «Выполнена» — номер `CLEAN` (кроме `OUT_OF_ORDER`), фиксируется факт времени.
3. Переходы проверяются на сервере: `NEW → IN_PROGRESS|CANCELLED`, `IN_PROGRESS → DONE|CANCELLED`; из `DONE`/`CANCELLED` переходов нет. Повтор целевого статуса идемпотентен — для офлайн-очереди.
4. Горничная меняет только свои задачи; менеджер и администратор — по праву `cleaning.manage`.
5. Новые права: `cleaning.manage` (ADMIN, MANAGER), `cleaning.execute` (ADMIN, MANAGER, MAID).

### 15.3 Интерфейсы

- Админ: `/admin/cleaning` — создание и распределение задач, отмена, матрица статусов номеров, отчёт по горничным, Excel (`report=tasks`).
- Горничная: `/m/tasks` — смена, задачи по приоритету, «Взять в работу» / «Готово»; офлайн-смены статусов уходят в очередь и применяются ровно один раз.
- Отчёт: `/api/reports/export?report=tasks&from&to`.

### 15.4 Вне объёма v2.4 (осознанно)

- Чек-листы с фотоподтверждением по пунктам — решение заказчика: достаточно статусов и задач.
- Автораспределение по секциям/этажам, нормативы времени по стандартам, push-уведомления, импорт заездов/выездов из PMS, таймлайн и аналитика чек-листов.

## 16. Чек-листы и мобильный интерфейс горничной (v2.5)

Основание: решение заказчика от 2026-11-05 (чек-листы нужны; PMS отсутствует, push не нужны) и образец TL Extranet «Обслуживание номеров»: дашборд, переключатель «Номера/Уборки», статусы, комментарии, проверка результата.

### 16.1 Чек-листы

| Сущность | Поля | Правила |
|---|---|---|
| `ChecklistTemplate` | название, описание, активность | Шаблон прикрепляется к задаче при создании или до начала работы (`attachToTask`); выключенный шаблон прикрепить нельзя |
| `ChecklistItem` | текст, порядок, обязательное фото, доп. вариант ответа | Пункт — плоский список (иерархия подпунктов вне объёма) |
| `ChecklistAnswer` | задача + пункт (уникально), ответ YES/NO/EXTRA, комментарий, фото, автор, время | Ответ можно изменить до закрытия задачи |

1. Задачу нельзя перевести в `DONE`, пока все пункты не отмечены и обязательные фото не загружены. Сервер отвечает: «Чек-лист не завершён: отмечено X из Y…».
2. Фото пункта: JPEG/PNG/WebP ≤ 5 МБ, тип по сигнатуре, хранение вне `public`, отдача только исполнителю задачи или праву `cleaning.manage`.
3. Права: шаблоны — `cleaning.manage`; ответы и фото — `cleaning.execute` для своей задачи.

### 16.2 Мобильный интерфейс (по образцу TL Extranet)

- **Главная**: смена, статистика моих задач и статусов номеров, быстрые действия.
- Вкладки: **Главная / Уборки / Номера / Ещё**.
- **Уборки**: фильтры «Активные / Выполненные / Все», карточки с приоритетом, чек-листом и статусом, переход в детали.
- **Детали задачи**: чек-лист с прогрессом, ответы «Да / Нет / Доп», фото пунктов, комментарий, действия «Взять в работу», «Уборка выполнена», «Отказ от уборки».
- **Номера**: свои номера с фильтрами по статусу уборки и ссылкой на активную задачу.
- **Ещё**: инвентаризация, раздача, сканер QR, очередь, выход.

### 16.3 Вне объёма v2.5

PMS-импорт заездов/выездов (PMS у отеля нет), push-уведомления (не требуются), иерархия подпунктов чек-листа, автораспределение задач и нормативы времени по стандартам.

## 17. Справочник, цена и дата (v2.6, M8A–M8B)

Основание: решения заказчика от 2026-11-05 — текущая цена справочника (без партий), остаток read-only, внедрение двумя шагами 8A → 8B.

### 17.1 Данные

| Поле | Назначение |
|---|---|
| `Item.priceKopecks` | Цена за единицу в копейках; только справочник, не операция |
| `Item.note` | Примечание позиции |
| `Operation.documentDate` | Дата документа; у приёмки — дата поступления |
| `WarehouseInventory.lastReceiptAt` | Дата последнего поступления (максимум из дат приёмок) |
| `Setting ui.showDates` | Глобальное отображение колонок дат |

Права: `catalog.manage` — управление справочником; `settings.ui` — переключатель дат.

### 17.2 Правила

1. Количество в справочнике — read-only остаток склада; количество вводится при приёмке.
2. Приёмка принимает дату; `lastReceiptAt` — максимум из дат, обратная датировка не «омолаживает» позицию.
3. Раздача/возврат/списание цену не запрашивают; стоимость считается по текущей цене справочника.
4. Инвентаризация показывает цену, стоимость расхождения и дату поступления; итог — сумма недостачи/излишка.
5. Отчёты: остатки (цена/стоимость/дата), движения по дате документа (цена/сумма), дефицит (стоимость), «позиции без цены».
6. Excel повторяет колонки отчётов; 1С получает `documentDate`, `unitPriceKopecks`, `totalKopecks`.
7. Удаление физическое только без истории: номер — без остатков/операций/инвентаризаций/задач; позиция — без остатка/операций/инвентаризаций.

### 17.3 Ограничение

Партии и FIFO не ведутся: при изменении цены историческая стоимость пересчитывается по текущей цене. Если потребуется историческая себестоимость — отдельный этап с `StockBatch`, текущие данные сохраняются.

### 17.4 Вне объёма v2.6

PMS-импорт, push, KPI, ретеншен, партии/FIFO, иерархия чек-листов, автораспределение задач.

## 21. QR-маршруты и хранение меток (v3.0, M12)

### 21.1 Публичные маршруты

- `GET /r/[code]` — номер по `number` или `id`; `GET /i/[code]` — позиция по `externalId`, `id` или имени.
- Без сессии — `/login?callbackUrl=<внутренний путь>`; форма входа поддерживает безопасный callback (только `/...`, не `//...`).
- После входа: номер — `/admin/rooms` (админ/менеджер) или `/m/rooms` (горничная); позиция — `/admin/catalog` или `/m`.
- Неизвестный код — 404; деактивированный объект — страница без действий.

### 21.2 Хранение

Таблица `QrCode`: одна активная метка на объект, уникальные `roomId`/`itemId`, поля `code`, `payload`, формат нагрузки/файла, `fileName`, MIME, размер, `baseUrl`; связи с `Room`/`Item` — `onDelete: Cascade`.

- Файлы: `storage/qr/<room|item>/<id>/<timestamp>.<png|svg>` вне `public`; отдача — `/api/qr/[id]` с правом `rooms.read`.
- Генерация на `/admin/qr` сохраняет файл и запись; повторная заменяет файл и запись (одна активная).
- Печать использует сохранённые метки, создаёт отсутствующие.
- Устаревание: смена номера, `externalId` или базового URL → статус «устарела» в QR-разделе, перегенерация вручную.

### 21.3 Удаление

- `catalog.delete` (позиция без остатка/истории): запись удаляется каскадом, файл — после успешного удаления; ошибка `unlink` логируется.
- `rooms.deleteRoom` (номер без истории): то же.
- `WRITE_OFF` (списание остатка) **не удаляет** позицию и её QR.
- Деактивация сохраняет QR; маршрут сообщает о деактивации.

### 21.4 UI-состояние предпросмотра

Результат генерации хранится с ключом объекта и параметров; при смене объекта/формата старый QR не показывается. Для объекта без нового результата показывается сохранённая метка (если актуальна) или предупреждение «устарела». Поздний ответ генерации по старому объекту игнорируется; кнопка блокируется на время запроса.

### 21.5 Вне объёма

История версий меток, автоматическая перегенерация, публичные карточки без входа.

- Точный контракт 1С не подтверждён публичной документацией; путь/метод настраиваются, проверка на тестовом контуре обязательна.
- Кнопка «Синхронизировать номенклатуру» переименована в «Загрузить номенклатуру»; она импортирует только позиции.

### 23.6 Гибкие свойства номеров (дополнение)

- Этаж: `floor Int?` или `floorName String?` — ровно одно; UI переключает «Число / Название».
- Тип: справочник `RoomType`; при вводе нового названия тип создаётся автоматически и используется в MinStock/отчётах.
- ADMIN (`rooms.manage`) создаёт, редактирует и удаляет номера/типы; MANAGER (`rooms.read`) видит страницу только для просмотра.
- Вход: «Настройки → Номера и типы комнат» (`/admin/rooms`); порядок группы: Общие настройки, Номера и типы комнат, Пользователи, Роли, Интеграция 1С; MANAGER видит доступные пункты в режиме просмотра.
- Редактируются номер, этаж и тип; удаление — только без истории, иначе деактивация.
- Миграции: `20261117090838_room_floor_custom_fields`, `20261117121500_rooms_manage_permission`.

### 23.7 Динамическое название бренда

- `generateMetadata()` читает `branding.hotelName`; title вкладки — `<название> — отель`, description и Apple title — с названием.
- Webmanifest отдаётся динамически через `/api/manifest` (`name`, `short_name`, `description`), без статического `public/manifest.webmanifest`.
- Смена названия в `/admin/settings` применяется после сохранения и `router.refresh()` без пересборки.
- Установленное PWA может сохранить старое имя до обновления/переустановки; service worker cache — `hotel-linen-v3`.
