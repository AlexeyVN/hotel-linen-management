# План: гибкие свойства номеров (этаж и тип)

Дата: 2026-11-17. Статус: **реализовано и выложено на `https://hotel`**.
Утверждено: этаж числом или названием, тип из справочника/новый тип, управление только ADMIN (`rooms.manage`), защита истории при удалении, редактирование номера/этажа/типа.
Задача: проверить соответствие проекта ТЗ; оценить добавление/удаление номеров с номером, этажом (число или свободное название) и типом (стандартный или свободное название); все настройки — администратор.

---

## 1. Соответствие текущего проекта ТЗ

ТЗ v3.2 требует:

- до 30 номеров и 3 этажей;
- `Room` — номер, этаж, тип, активность;
- `RoomType` — редактируемый справочник (добавление/переименование/деактивация), а не enum;
- номера: список, фильтры, поиск, добавление, редактирование, деактивация;
- физическое удаление номера — только без истории, иначе деактивация;
- права `rooms.read`/`rooms.write` у ADMIN и MANAGER (ТЗ §6.2).

Фактически:

| Требование | Состояние | Комментарий |
|---|---|---|
| Список/фильтры/поиск номеров | выполнено | `/admin/rooms`, фильтр по этажу/типу |
| Добавление номера | выполнено | номер, этаж (число 1–20), тип из справочника |
| Удаление номера | выполнено с защитой | API блокирует удаление при истории, предлагает деактивацию |
| Типы комнат | выполнено | добавление, переименование, включение/выключение; удаления типа нет |
| Этаж | ограничено | `Int`, 1–20; свободное название невозможно |
| Тип | ограничено | только существующий `RoomType`; произвольное имя — через создание типа |
| Редактирование номера/этажа | не выполнено | в таблице меняется только тип; номер/этаж задаются при создании |
| «Все настройки — администратор» | не выполнено | `rooms.write` есть и у MANAGER по ТЗ |
| Масштаб 30 номеров | совместимо | ограничения 1–20 этажей, 10 символов номера |

Итог: текущая реализация **соответствует ТЗ v3.2**, но новый запрос — расширение модели: свободный этаж, свободный тип и управление только ADMIN.

## 2. Варианты модели

### Этаж

**A. Число + необязательное название (рекомендуется)**

```
Room.floor      Int?      // для числовых этажей и сортировки
Room.floorName  String?   // свободное название, если число не задано
```

- Ровно одно из полей заполнено (валидация Zod).
- Существующие номера сохраняют `floor`; миграция не меняет данные.
- Отображение: `floorName ?? String(floor)`.
- Фильтр/сортировка: числа сначала по возрастанию, затем названия по алфавиту.
- Минимальные изменения API/отчётов.

**B. Только строка `floorLabel`**

- Проще формально, но ломает текущие `Int`-фильтры, сортировку, отчёты и тесты; требует миграции всех данных и API.
- Не рекомендуется.

### Тип

**A. Справочник + создание «на лету» (рекомендуется)**

- Админ выбирает стандартный тип или вводит новое название; система создаёт `RoomType` с автокодом (`CUSTOM_...`) и сразу назначает номеру.
- Тип остаётся единым справочником: работает `MinStock`, отчёты и фильтры.
- «Свободное название» = новый тип в справочнике, а не текст в каждой комнате.

**B. Произвольный текст в номере (`Room.typeName`)**

- Максимальная свобода, но дубли, разные написания и отсутствие правил минимальных остатков для произвольных типов.
- Требует nullable `roomTypeId` и переработки `MinStock`/отчётов.
- Не рекомендуется без отдельного запроса.

### Права

**A. Новое право `rooms.manage` только ADMIN (рекомендуется)**

- MANAGER сохраняет `rooms.read` (просмотр), но не создаёт/не удаляет номера и типы.
- Требует seed/миграцию permission, обновление пресетов и тестов; ТЗ §6.2 меняется.

**B. Оставить `rooms.write` у ADMIN и MANAGER**

- Соответствует текущему ТЗ, но не соответствует формулировке «все настройки делает администратор».

### Удаление

- Сохранить текущую защиту: удалять только номер без истории, иначе деактивировать (ТЗ).
- Дополнительно можно разрешить удаление **неиспользуемого типа** (нет номеров) — безопасно.

## 3. Предлагаемый объём

1. **Схема и миграция**
   - `Room.floor Int?`, `Room.floorName String?`; CHECK на уровне приложения (Prisma/SQLite).
   - Валидация: номер 1–10 символов, уникален; этаж — либо целое 1–99, либо текст 1–40; ровно одно.
   - `RoomType` остаётся справочником; добавить автогенерацию кода для нового типа.
2. **API `rooms`**
   - `createRoom`: `{number, floor?: number, floorName?: string, roomTypeId?: string, newTypeName?: string}`.
   - `updateRoom`: номер/этаж/тип (сейчас только тип).
   - `deleteRoom`: без изменений (история → отказ).
   - `createType`: поддержать автокод, если админ вводит только название.
   - `list/floors` возвращают `floorLabel`; фильтр по числу/названию.
   - Мутации — `rooms.manage` (ADMIN). `rooms.read` — все, кому положено.
3. **UI `/admin/rooms`**
   - Форма: номер; переключатель этажа «Число / Название»; поле; тип — select + «Новый тип» (inline).
   - В таблице: редактирование номера/этажа (не только типа), тип, статус, удаление.
   - Все действия создания/удаления/типов — только ADMIN; менеджеру показывать read-only и подсказку.
   - Ошибки: дубликат номера, пустой этаж, занятое имя/код типа.
4. **Отчёты/QR/уборка**
   - Везде отображать `floorLabel`; QR payload и маршруты не меняются.
   - Excel-колонка «Этаж» — строка.
5. **Тесты**
   - API: числовой/текстовый этаж; стандартный/новый тип; дубликат; удаление с историей/без; менеджер 403.
   - UI Playwright: создание, редактирование, удаление, фильтр по названию этажа, мобильная ширина.

---

## 4. Критерии приёмки

1. ADMIN создаёт номер с числовым этажом и с этажом-названием; оба видны в списке/фильтре.
2. ADMIN выбирает стандартный тип или вводит новый — тип появляется в справочнике и назначается номеру.
3. ADMIN редактирует номер, этаж и тип существующего номера.
4. Удаление без истории работает; с историей — отказ и предложение деактивации.
5. MANAGER не может создавать/редактировать/удалять номера и типы (если выбран ADMIN-only).
6. Дубликат номера/типа — понятная ошибка, не 500.
7. Отчёты, QR и уборка не ломаются; тесты/build зелёные.

| 1 | Модель этажа | `floor Int? + floorName String?` / только строка | **Int + название** |

## 6. Реализация и проверка

- Миграции: `20261117090838_room_floor_custom_fields` (`floor Int?`, `floorName String?`), `20261117121500_rooms_manage_permission`.
- Право `rooms.manage` только ADMIN; MANAGER — `rooms.read`, страница номеров read-only; существующий `rooms.write` оставлен для совместимости, но маршруты используют `rooms.manage`.
- API: создание/редактирование номера с числовым или текстовым этажом, inline-создание типа по названию, редактирование номера/этажа/типа; удаление только без истории.
- UI `/admin/rooms` (пункт «Настройки → Номера и типы комнат»): переключатель «Число / Название», поле нового типа, inline-редактирование, скрытие управления для менеджера.
- Отображение `floorLabel` обновлено в уборке, мобильных задачах/номерах; отчёты и QR не затронуты.
- Playwright: создан номер с текстовым этажом и новым типом; номер/этаж изменены; номер удалён; менеджер видит read-only; 0 ошибок.
- Тесты 88/88, build; миграции применяются; тестовые записи удалены.
